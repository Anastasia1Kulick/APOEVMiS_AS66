# Лабораторная работа 1 — вариант 6

Задание: нечётные символы строки заменить на символ `+`.
Основание: лекционный материал и лабораторный курс АПО ЭВМиС, страницы 271–272.
Пример: `abcdef` → `+b+d+f`; `Привет` → `+р+в+т`.

## Соответствие заданию

- `src/transform.cpp`: две отдельные функции обработки одной и той же строки.
  `replace_cpp` написана на C++, `replace_asm` содержит ассемблерную вставку.
- Реализация для macOS на Apple Silicon использует вставку ARM64. Работа на Mac согласована с преподавателем.
- Дополнительно включена ветка Intel x86 для MS Visual Studio / Win32; полный запуск в Visual Studio не выполнялся.
- Есть проверка правильности, демонстрация и сравнение быстродействия.
- Готовый отчёт находится в `../rep/report.docx`.

## Как запустить на Mac

Из папки лабораторной в Терминале:

```sh
bash run_mac.command --demo
bash run_mac.command --test
bash run_mac.command --bench
```

Без параметра программа предложит ввести строку. Можно также открыть
`run_mac.command` двойным щелчком, если macOS разрешает его запуск.
Программа собирается в `build/lab1`. Нужен настроенный Clang из инструментов
Apple. Если появляется сообщение о лицензии Xcode, пользователь должен
самостоятельно ознакомиться с ней и принять её, если согласен.

`--demo` показывает результаты на готовых примерах, `--test` выполняет
проверки, `--bench` измеряет скорость. Бенчмарк показывает архитектуру и
версию компилятора, чтобы результаты ARM64 не приняли за результаты Intel.

## Как проверить в MS Visual Studio

Готовый проект для Visual Studio 2022 с инструментами C++ v143:
`src/Lab1.vcxproj`. Он уже настроен на Release / Win32 и C++17.
Если используется другая версия инструментов, можно перенастроить toolset
в свойствах проекта либо создать проект вручную:

1. На Windows создать консольный проект C++ без предкомпилированного заголовка.
2. Добавить `main.cpp`, `transform.cpp`, `transform.h`, `utf8.h` из `src`.
3. Выбрать платформу **x86 / Win32**, конфигурацию **Release**, стандарт C++17,
   кодировку исходников UTF-8 (`/utf-8`). Сборка x64 намеренно не поддержана:
   MSVC не поддерживает в ней встроенный `__asm`.
4. Собрать и запустить программу; для проверки использовать `--test`, для
   сравнения скорости — `--bench` в аргументах запуска.
5. Альтернатива: открыть **x86 Native Tools Command Prompt for VS** и запустить
   `src/build_windows.bat`, затем `build\lab1.exe --demo` и `--bench`.

Ограничение MSVC: https://learn.microsoft.com/en-us/cpp/assembler/inline/inline-assembler

## Как устроено решение

Нечётные позиции 1, 3, 5 соответствуют индексам массива 0, 2, 4.
Функция заменяет каждый второй элемент, начиная с первого. Чётные позиции
остаются без изменений, длина строки сохраняется. Для пустой строки ничего
не записывается. Число замен равно `n / 2 + n % 2`.

Ввод и вывод используют UTF-8. Перед обработкой строка преобразуется в
`std::u32string`: одна кодовая точка Unicode занимает один элемент `char32_t`
размером 4 байта. Поэтому русский текст не повреждается, как при замене
отдельных байтов UTF-8. В обеих реализациях используется один и тот же формат.
Составной эмодзи или буква с отдельным комбинируемым знаком может состоять
из нескольких кодовых точек: именно их, а не графические группы, считает
программа. Преобразование кодировки не входит в измеряемое время.

### Intel x86

- EAX хранит адрес текущего символа.
- ECX хранит число оставшихся замен.
- EDX хранит 43 — код символа `+`.
- `mov dword ptr [eax], edx` записывает плюс.
- `add eax, 8` переходит через один элемент: два символа по 4 байта.
- `dec ecx` уменьшает счётчик, `jnz` повторяет цикл.
- Начальные `test` и `jz` защищают пустую строку.

### Mac ARM64

`str` записывает символ, `add` передвигает указатель, `subs` уменьшает счётчик
и устанавливает флаги, `b.ne` повторяет цикл. `cbz` обрабатывает нулевой счётчик.
Операнды и изменяемые регистры объявлены компилятору явно; `memory` сообщает,
что вставка меняет память. Здесь используется другой набор инструкций.

Обе функции работают за O(n) времени и используют O(1) дополнительной памяти.
Внешнее преобразование UTF-8 и копии для сравнения требуют O(n) памяти.

## Проверки

- 11 примеров с заранее известным результатом: пустая строка, один символ,
  чётная и нечётная длина, пробелы, плюсы, русский текст, эмодзи, управляющие
  символы. Обе функции проверяются вместе с контрольными элементами по краям.
- 1025 длин от 0 до 1024: отдельно проверяется каждый символ и завершающий ноль.
- Проверяются преобразование UTF-8 туда и обратно и отклонение пяти типов
  некорректного UTF-8.

Успешность реального запуска подтверждают только файлы в `results`.
Отсутствие результатов не означает, что программа уже проверена.

## Методика сравнения скорости

Сборка Mac: C++17, `-O2`, без LTO. Обе функции вынесены в отдельный файл и
запрещены для встраивания. Вызовы через volatile-указатель не дают компилятору
удалить повторные вызовы. C++ может оптимизироваться и векторизоваться:
это нормальная часть сравнения.

Длины: 16, 256, 4096, 65536 кодовых точек. Для каждой длины выполняются семь
раундов, порядок двух функций чередуется, выводится медиана времени одного
вызова в наносекундах. Количество повторов выводится рядом. Копирование,
выделение памяти, ввод, вывод и проверка результата вынесены за интервал
измерения. Используются монотонные часы `std::chrono::steady_clock`.

Измеряется многократная обработка одного прогретого буфера. После первого
вызова нечётные позиции уже содержат плюсы, но каждый последующий вызов
снова выполняет записи. У обеих функций одинаковые условия. Эти результаты
не описывают ввод с клавиатуры или обработку холодной памяти.

Отношение `cpp_div_asm` — время C++ / время ASM. Больше 1: быстрее ASM;
меньше 1: быстрее C++. Ассемблерная вставка не обязана быть быстрее:
оптимизатор C++ может построить более эффективный код. Вывод делается по
фактическим измерениям конкретной архитектуры и конфигурации.

## Результат

Программа проверена на Mac ARM64 с Apple Clang 21.0.0. Все проверки правильности и проверка с AddressSanitizer / UndefinedBehaviorSanitizer прошли. Журналы находятся в `results/`.

В измеренных сценариях C++ оказался быстрее данной ассемблерной реализации примерно в 1,6–2,35 раза. Подробные результаты и выводы приведены в отчёте.
